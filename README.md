# Angband 자동 QA 파이프라인

오픈소스 로그라이크 **Angband**의 무기 수식자(브랜드/슬레이) × 몬스터 특성
상호작용 규칙을 결정 테이블로 전수 생성하고, 실제 게임 엔진에 실행시켜
문서화된 규칙과의 불일치를 찾아내는 QA 자동화 파이프라인.

## 무엇을 검증하는가

Angband에서 무기에 붙은 **브랜드**(화염/냉기/산성 등 원소 부여)와
**슬레이**(오크/언데드/악 등 종족 특효)는 몬스터의 저항·취약·종족 플래그와
맞물려 최종 데미지 배율을 결정한다. 규칙은 단순해 보이지만 조건 변수가
7개라 조합이 수천 가지로 늘어나고, 사람이 손으로 전수 검증하기 어렵다.

이 파이프라인은 그 조합을 자동으로 전개해 실제 엔진에 돌린다.

## 어떻게 검증하는가 (차분 테스트)

```
brand.txt / slay.txt            docs/domain-mapping.md
   (선언적 게임데이터)              (문서화된 규칙 6개)
          |                              |
          +--------------+---------------+
                         v
              reference_model.py  ← 구현 코드를 보지 않고 독립 구현
                         |
                    기대 결과
                         |
   결정 테이블 전개 →  2,664 케이스  →  C 하네스 렌더링
                                            |
                                    실제 Angband 엔진 실행
                                            |
                                        실제 결과
                         |                  |
                         +------- diff ------+
                                  |
                              불일치 리포트
```

핵심은 **기대값을 구현 코드에서 가져오지 않는다**는 점이다. 참조 모델은
게임데이터와 문서화된 규칙만으로 독립 작성했다. 구현을 그대로 옮기면
파이프라인이 자기 자신과 비교하게 되어 아무것도 검증하지 못한다.

## 실행

```sh
scripts/setup-angband.sh    # 최초 1회 (클론 + 빌드, 수 분 소요)
qa/pipeline.sh              # 전체 회귀
```

불일치가 있으면 exit 1로 종료하므로 CI 게이트로 바로 연결할 수 있다.

## 현재 결과

| 항목 | 값 |
|---|---|
| 커버 대상 | 브랜드 10종 × 슬레이 11종 전체 |
| 생성 케이스 | 2,664 |
| 불일치 | 0 |
| e2e 스모크 (race × class) | 99/99 통과 |

전 케이스 일치는 "테스트가 무력하다"는 뜻일 수도 있으므로, 엔진을 일부러
훼손해 파이프라인이 이를 검출하는지 확인했다(mutation test):

| 하네스 관측 범위 | 훼손 시 검출 건수 |
|---|---|
| 선택된 수식자 + 동사만 관측 | 4 |
| **배율까지 직접 관측 (현재)** | **28** |

배율 변화가 "승자를 뒤집을 때만" 잡히던 사각지대를, 엔진의 배율 계산 함수를
직접 호출해 관측하도록 보강해 해소했다.
